# ReBorn behaviours

ReBorn is re-created as Lua on Sacred Gear's APIs, not copied as bytes. This file is the list of behaviours the Lua has to
reproduce: what vanilla does, what ReBorn does, and which Gear API the Lua version needs. Source of the facts:
`out/analysis.md` and `out/hunks.json` (generated by `tools/reborn_port.py`), the English decompile (`decomp-sacred`) and
the German -> English map. English addresses unless marked DE.

Status per row: **decoded** (understood), **characterised** (where and how it changes is known, the game meaning is not),
**engine** (not gameplay; Bild or the data layer covers it). Field names are used only where a consumer proves them;
the rest are `unk_<offset>`.

## B1/B2 The ability table: one id-keyed `gear.data.abilities[id]`

The exe has two record tables that are looked up by the same kind of id. `FUN_004d1af0(id)` scans **T1** (ENG `0x94FE28`, 94
records of 0x78 bytes, ids 1000, 1001, 1002, 1009, 1057 ...), `FUN_004d2310(id)` scans **T2** (ENG `0x952ACC`, 70 records of
0x94 bytes, ids 1, 2, 3 ...). Code that has an id tries T1 first and falls back to T2 (`FUN_004fe870`, `FUN_006d60e0`), and
both records have a `target_mode` byte that is passed on the same way, so they are one ability table split by id range.
About 80 callers each (`FUN_005bb010` creature action handler, `FUN_00571710`, `FUN_005796a0`, the tooltip `FUN_006a6550`, ...).
**What they are:** the names in the game's own texts (read through `gear.text.get` by `tools/abilitydump`, `data/ability_names.json`) say **T1 = the combat
arts** (`1000` Rundumschlag / "sweep", `1001` Harter Schlag, `1002` Attacke, `1003` Stampfsprung, `1004` Explosionspfeil ...) and **T2 = the spells**
(`1` Phasenverschiebung, `2` Steinhaut, `3` Gefaehrtin des Waldes, `4` Wasserform, `5` Feuerball ...). The Lua API still exposes one table by id
(`gear.data.abilities[id]`, with `.kind` = `'combat_art'` or `'spell'`). The names are German because that was the game's language in the dump run.

### T1 record (0x78 bytes)

| Offset | Type | Name | Evidence |
|---|---|---|---|
| +0x00 | i16 | `id` | lookup key |
| +0x04 | u32 | `name_text` | text id of the name: proven (`gear.text.get` gives the combat art's name for all 94) |
| +0x08 | u32 | `description_text` | text id of the description: proven (the descriptions come back for all 94) |
| +0x4C | u32 (read as byte) | `target_mode` | proven: passed as the mode of `FUN_0051d840`; same use as T2 +0x3C |
| +0x50 | f32 | `effect_base` | proven: `level * effect_per_level + effect_base`, level 1..100 (`FUN_005bb010` case 0xBFC, `FUN_005796a0` case 0x3F7) |
| +0x54 | f32 | `effect_per_level` | proven (same) |
| +0x58 | f32 | `effect2_base` | proven: second pair in `FUN_005bb010` |
| +0x5C | f32 | `effect2_per_level` | proven |
| +0x40, +0x44 | f32 | `unk_40`, `unk_44` | not decoded (floats, 5.0 / 3.0 / 6.0 -> 2.0..4.0) |
| +0x60, +0x64, +0x68, +0x6C, +0x74 | u32 | `unk_60` ... | not decoded (`unk_60`: 1000 -> 250 in 16 records, looks like milliseconds) |

### T2 record (0x94 bytes)

| Offset | Type | Name | Evidence |
|---|---|---|---|
| +0x00 | i16 | `id` | key |
| +0x04 | u32 | `name_text` | proven: `gear.text.get` gives the spell's name for all 70 |
| +0x08 | u32 | `description_text` | proven: the description text for 59 of 70 (the others have none) |
| +0x3C | u8 | `target_mode` | proven (as above) |
| +0x42 / +0x44 | i16 | `value0_base`, `value0_per_level` | proven: tooltip `FUN_006a6550` computes `level * per_level + base` |
| +0x46 / +0x48 | i16 | `value1_base`, `value1_per_level` | proven |
| +0x4A / +0x4C | i16 | `value2_base`, `value2_per_level` | proven |
| +0x4E / +0x50 | i16 | `value3_base`, `value3_per_level` | proven |
| +0x3E, +0x40, +0x52 ..+0x90 | u16 | `unk_3e`, `unk_40`, `unk_52` ... | not decoded: progressions and flags (`unk_76` and `unk_82` are edited 42 and 36 times) |

### What ReBorn changes

`data/abilities_edits.json` is the generated per-id edit table (vanilla -> ReBorn per field, `tools/abilities.py`):
- **T1:** 92 of 94 records, 367 field edits. By field: `unk_40` 88, `unk_44` 71, `effect_base` 70 (0.8 -> 1.45 / 2.4), `effect_per_level` 44
  (0.1 -> 0.05), `effect2_base` 30, `effect2_per_level` 28, `unk_60` 16 (1000 -> 250), `unk_64` 9, `target_mode` 2 (1 -> 3), a few others.
- **T2:** 59 of 70 records, 414 field edits: `unk_3e` 55, `unk_40` 51, `unk_76` 42, `unk_82` 36, the `value0..3` pairs about 18 each, the rest in
  `unk_52 .. unk_90`.

The Lua mod holds this table as data (`edits = {[1000] = {effect_base = 1.45, ...}}`); regenerating it after a new ReBorn release
is one command.

### Proposed Lua shape (to confirm before any Gear code)

```lua
local a = gear.data.abilities[1000]     -- routes to T1 or T2 by id; nil if unknown
a.effect_base = 1.45                    -- named fields only where a consumer proves them
a.unk_60 = 250                          -- everything else by offset name, marked unproven
a.table                                 -- 'T1' | 'T2' (read only)
gear.data.abilities:apply(edits)        -- {[id] = {field = value, ...}}, one call, validated
```

- Each table has its own field layout (a layout table in Gear); a field that does not exist for the record's table is an error.
- Writes go to the exe's live tables (the engine reads them each time), are checked for type and range, and are restored on unload.
- Reads work the same way, so the Lua can also compute from vanilla values.

## B3 Data paths (engine)

`bin\%s` -> `SRB\%s`, `.\SRB\Balance.bin`, `MODELS` -> `SRmdls`, `CREATURE.PAK` -> `SRcreate.PAK`, `WEAPON` -> `SRwpon`,
`ITEMS.PAK` -> `SRitm.pak`, `GLOBAL` -> `SRglbl`. In the mod these are not patched: the **Gear file overlay** serves
`mods/reborn/data/...` for the original path, from the manifest. **Gear API:** `gear.files.overlay` (to add).

## B4 Text (engine)

`cTextTable::load` (ENG `0x80E680`) is rewritten to read `SRglbl.res` from disk. In the mod: the text file is loaded through
Bild's existing `cTextTable::load` hook. **Gear API:** `gear.text.load(path)` (to add), and `gear.text.get(id)` to read the
game's text by id (needed to name abilities: the ids in the ability tables are not keys of `global.res` but go through the game's
own lookup).

## B5 World object culling, `FUN_00566070` (37 hunks)

The visible-rectangle expressions of the object pass (view minus 1.0 over viewport sizes from `0xAD44E8..`) are replaced by fixed
constants (`5.0`, `40.0`, `0.5`) so that objects are culled the same way at any screen size. Engine; read, not tested.

## B6 Creature AI: which ability a creature uses, `FUN_004d4e50` (14 hunks) - decoded

`FUN_004d4e50` (26 KB) is the creature AI step. It stores the ability the creature is about to use in **`[creature + 0x120]`**
(`param_1[0x48]`): a **T2 id** (small numbers) or a **T1 id** (0x3E9.. = 1001..), chosen per creature type (`param_1[4]`).
ReBorn changes which ability some creature types pick:

| Site (ENG) | Vanilla | ReBorn | Context |
|---|---|---|---|
| `0x4D534A` | ability 25 | 23 | a branch that fires on a random chance (`rand() % (n+1) == 2`) when an enemy is in range and a free target exists |
| `0x4D5754` | 29 | 33 | creature types `0x2C`, `0x40`, `0x41` |
| `0x4D5E68` | `50 - (x % 3 != 0)` (49 or 50) | 49 | creature chooses between two abilities depending on a modulo of a counter: now fixed |
| `0x4D60ED` | 40 | 5 | a branch that otherwise picks 40 |
| `0x4DA600` | 40 | 34 | another site that picks 40 |
| `0x4D80DD` | base 1067 (`0x42B`) | 1049 (`0x419`) | `add eax, base`: an id base the AI adds an offset to (context not read) |
| `0x4D7068` | `jne` | `je` | a condition is inverted |
| 7 sites `0x4DA04B ..0x4DA237` | `call 0x562330` | `call` a copy of it in the PE header (`0x4007C0`) | the AI keeps using the vanilla version of the "add to a creature's effect entry, clamp to its maximum" function (`FUN_00562330`), which ReBorn itself changes for everyone else (hook into appended code, B9) |

The ability numbers are the T2/T1 ids of B1/B2, so these edits are only meaningful once the abilities have names.
**Gear API:** a hook on the creature AI's choice (`gear.on('creature.ability', c, id) -> id`) is the clean version; this cannot be expressed
from data alone.

## B7 Record layout shift, `FUN_005abd80` (31 hunks)

16-bit stack slots at `esp+0x3A, +0x3C, +0x3E` ... move to `+0x3C, +0x40, +0x44`: they are widened to 4 bytes in a 3471-line function
(some ids or counts that exceed 16 bits). Not decoded.

## B8 The three Settings.cfg features - decoded

ReBorn reads three more keys of `Settings.cfg` at startup, in code it appended (`.rsrc` caves in ReBorn's image at `0x1AD9AC0..0x1AD9D97`), and applies
them as follows:

| Key | When set | Effect |
|---|---|---|
| `SR_QUICK_CAST` | flag byte `[0x1ACCFB0] = 1` | in the skill-slot window handler (ENG `0x6E1BC0`, four call sites) a cave sends the engine (`FUN_006172c0`, the event handler) a synthetic event at the current cursor position (`[0x182CD98]`, `[0x182CD9C]`): pressing a slot key casts at the cursor immediately |
| `SR_RESISTANCE_GLOW` | writes 0 over the immediate of an `and ecx, 0x40007800` at DE `0x44BA58` (ENG function `0x44B230`) | clears the item-flag mask passed to an item draw, which changes the glow/colour flags of resistance items |
| `SR_UPSCALING` | `push 0` -> `push 1` at DE `0x630503` and a 2-byte jump removed at DE `0x630A27`, both in ENG function `0x62FF60` | a render-state switch in the world render function (engine) |

**Gear API (implemented):** `gear.settings.game(key)` reads `Settings.cfg`; the event `skillslot.select` (five site hooks in ENG `0x6E1BC0`, after a digit key chose
a slot: four `mov byte [esp+0x13], 1` that follow the `call 0x6E1A20` selection and the last `call` itself) and `gear.game.cursor_click()`, which sends the
engine's window event handler (ENG `0x6172C0`, found by a window 0x30 bytes inside because SacredBild detours its start) a mouse **button down** event
(class vtable ENG `0x89704C`, the signature pairing of ReBorn's `0x8950A8`; type 2, the cursor `0x182EE18/1C`) at the object ENG `0xAD6EF8`, as ReBorn's cave does;
`gear.game.cursor_click(false)` sends the button up class (`0x899248`) instead. `mods/reborn` clicks when `SR_QUICK_CAST` is `1`.
**Verified in real play (pointed run, `-SlotKeys`):** the five slot sites fire on a digit key whether it is typed as a character, pressed or held,
**but only with `COMBINE_SLOTS : 1` in `Settings.cfg`**: the handler asks the setting (ENG `0x81CF80`, string `COMBINE_SLOTS`) before it selects a slot;
with 0 the keys never reach the sites. **Not verified:** that the injected event makes the game act: with no skill chosen a direct `cursor_click()`
did not walk the hero (event position equals the mouse's, `597,341`), so either the world mouse handler needs more than the event (SacredBild's
hook remaps its position, the button state of `cMouse` ...) or a click needs a chosen skill. Still to find out with a hero that has a skill selected.
ReBorn's other change in that handler (a cave at `0x1ACC770` that routes the keys `1`..`7` to the slot actions) is not re-created. RESISTANCE_GLOW and UPSCALING are rendering: Bild.

## B10 "Branch changes" (63 hunks)

`data/branch_changes.json`. 46 are `mov/push/add/call -> jmp`: jumps into code ReBorn appended in the PE header (`0x400300..0x400FFF`)
and the other caves; they sit mostly in UI and startup functions (`dxDriver7_drawLoadingScreen` `0x6468A0`, `cUI_Manager::createGameWindows`

(`ja -> jbe` x4 in `FUN_005abd80` (B7), `jne -> je` x3, `je -> jmp` x5, ...); each needs its context read.

## B11 Damage and effect values widened to 32 bits (about 60 hunks in 11 functions) - decoded

Vanilla keeps damage, effect and level values in 16-bit (and 8-bit) slots and clamps them: `cmp eax, 0xFFFE; jbe ...; mov eax, 0xFFFE`
(65534), `and ebx, 0xFFFF`, `mov dword [esp+0x34], 0xEFFF`, and the hero's skill level `[creature+0x249]` is a byte. ReBorn changes the slots to
32 bits (`mov word [esp+0xAC], ax` -> `mov dword [esp+0xAC], eax`, `mov dl, [ebp+0x249]` -> dword) and removes the clamps (the `cmp/mov 0xFFFE`
instructions become nops). Functions: `FUN_0050E6C0` (13 hunks), `FUN_00514790`, `FUN_0055FE20`, `FUN_00562730`, `FUN_0056B130`, `FUN_005AA7E0`,
`FUN_005B2600`, `FUN_005BB010`, `FUN_00582D50`, `FUN_00571710`, the stack-slot shift of B7 (`FUN_005ABD80`) belongs here too. Effect: damage and
effect values above 65534 do not wrap or saturate, which the item and ability numbers of ReBorn's balance (T1/T2 values, `balance.bin` limits
`5500..8500 -> 2000`) rely on. **Not re-creatable from data**: the widths are in the engine's structures. A Lua version needs a damage hook that
returns a 32-bit value; see the hooks below.

**Decision (John, 2026-11-15): the Lua port keeps the engine's 16-bit damage.** Damage and effect values are not widened, the 65534 cap stays.
This is a deliberate deviation from ReBorn: ReBorn's numbers above 65534 do not exist here (they wrap/saturate to 65534 as in vanilla).
How far that matters is measured, not guessed: ReBorn's T2 `base + L*per` reaches at most 25755 (level 100), 38505 (150), 55335 (216), 65280 (255,
ability 69), T1 `effect1` at most 43200 (216); so the ability values themselves stay below the cap up to level 255, only sums with items and
multipliers could exceed it (not measured: no high level hero save).
**Gear API:** `gear.on('damage', function(hit) -> damage)` is a site hook (ENG `0x56DAAB` in `FUN_0056B130`: the `call __ftol` that turns the final
float damage into the integer the function returns, before the immunity checks); `hit = {damage, victim_type, attacker_type}`; the result is clamped to
0 .. 65534. ReBorn changes no damage rule beyond the widening and the constants (B12, B13 are applied through `level.factor` and `combat.constant`),
so the reborn mod does not register a damage handler (its self test only exercises the stub); the hook is there for mods that shape damage.

## B12 Level tiers instead of a smooth level function (5 hunks) - decoded

`FUN_0051CC30` (and its three inlined copies in `FUN_0050E6C0` x2 and `FUN_005893B0` x3) turn a level into a factor. Vanilla:
`(34 * L + 8) / (c1 * L + c2)` (a smooth rational function, constants `0x88F0B4` = 34.0, `0x88E918` = 8.0, `0x88E9EC`, `0x88F0B0`).
ReBorn: integer tiers, `1 + (L > 12) + (L > 24) + (L > 36)`: 1 up to level 12, 2 up to 24, 3 up to 36, 4 above. The same replacement at all
five sites, so one Lua function (tier of a level) is enough, but it has to be used by the engine: **hook** `gear.on('level.factor', level) -> n`
(this is also what the functions around those sites compute: monster level scaling).

## B13 Combat constants moved to a table in the PE header (about 20 hunks) - decoded

`fmul dword [0x88EDA0]` (0.2) -> `[0x400B25]` (1.0) in `FUN_005038F0`, `FUN_00506770`, `FUN_0050AC00` and `FUN_0050E6C0` (the four hit
handlers, together with a branch each: `jne -> je` / `je -> jmp` that skips a condition), and `fmul dword [0x88ECB0]` (0.01) ->
`[0x400FC4]` (0.01) / `[0x400FC8]` (0.05) in `FUN_00559BF0` (three sites), `FUN_0056B130` -> a jump into appended code.
`FUN_0056B130` also loads five factors `1.0, 1.34, 1.67, 2.0, 2.34` (`0x88E66C, 0x88EDF0, 0x88EDEC, 0x88E750, 0x88EDE8`) from ReBorn's
table as `1.06, 1.08, 1.10, 1.12, 1.14` (`0x400FAF..0x400FBF`): the per-difficulty or per-tier damage factors become much flatter.
Needs the constants exposed: **API** `gear.data.constants` (named float table of the exe's combat constants) or the damage hook.

**Branch flips (re-created):** the five conditional jumps ReBorn flips in the hit handlers (ENG `0x505230` `jne -> je`; `0x505395`, `0x5074E7`, `0x50BA2A`,
`0x50F27C` `je -> jmp`) are site hooks of the event `combat.branch(name, vanilla, index) -> boolean`. The four `je` follow the creation of an effect object
(types `0x34B`, `0x360`, `0x35C`, `0x35E`) and skip the secondary effect added when the object exists: ReBorn always skips it; `0x505230` tests for
the combat art `0x3FC` and is inverted. `mods/reborn` answers them; `hit.secondary[1]` ran twice in real play.
Three more flips outside the hit handlers use the same event (they are `jcc rel8`, the next instruction is copied into the stub; the handler also gets `eax`):
`ai.timer` (ENG `0x4D7068`, `cmp eax, 0xB7; jne -> je`: the AI timer default 300 / 700 swaps between creature type 0xB7 and all others),
`ability.dispatch` (`0x51DA04`, `cmp eax, 0x28; jge -> je`: only the ability 0x28 takes the jump, 0x29 no longer) and `color.clamp` (`0x4DEF0B`,
`cmp word [esp+0x30], 0xFF; jbe -> jmp`: the clamp to 255 is never applied). Not re-created: B7 (`0x5AF7D7..0x5AF827` `ja -> jbe`, tied to the widening that stays 16 bit)
and the engine/graphics flips (`0x644164`, `0x645FBA`, `0x6AC343`, `0x6DFDAE`, `0x84C0E1`).

## Hook sites for B12 and B13 (`data/hook_sites_b12_b13.json`): code sites, not data

ReBorn does not change the constants' data: it points individual instructions at other constants. The pooled floats are shared by many users
(`0.2` at ENG `0x890DA0` has 29 users, `0.01` at `0x890CB0` 331, the difficulty factors 64 each, `1.0`/`2.0` 110), so a `gear.data.constants` write
would change every user, not the four hit handlers. The 23 sites are instructions inside functions:
- **B12 (6):** `FUN_0051CC30` (one caller, `call` at `0x511DFD` in `FUN_0050E6C0`) and five inlined copies of the same 8-instruction expression
  (`0x51065A`, `0x5113C3` in `FUN_0050E6C0`; `0x58E516`, `0x58E59A`, `0x58E611` in `FUN_005893B0`): `fild level; ...; fdivp; call __ftol`.
  There is no shared helper for the inlined ones.
- **B13 (17):** the hit handlers' two `fmul [const]` each (`0x505439`, `0x505624`, `0x50758F`, `0x507793`, `0x50BACC`, `0x50BCB4`, `0x50F31D`,
  `0x50F516`), three in `FUN_00559BF0` (`0x559F08`, `0x55A149`, `0x55A248`), five `fld [const]` and one `fmul` in `FUN_0056B130` (`0x56D0DB..0x56D110`,
  `0x570956`). ReBorn's replacements are 1.0 (`0x400B25`), 0.01 / 0.05 (`0x400FC4` / `0x400FC8`), the five factors 1.06..1.14 (`0x400FAF..BF`), and
  `[0x400625]` / a jump to appended code (`0x400AA0`), which are not plain constants (a variable or code).

## Hook sites in real play (self test with `-Fight`, `tools/fightcal`)

The hero was made to play with automation input (spawned skeleton and orc warriors, Shift + click melee swings, tooltips in the inventory and character
windows, belt tooltips, right clicks with the belt's right hand combat art) and every site's run count was read through `gear.hooks.sites()`:
- **Reached by the hero's combat art (right mouse button):** `hit.effect_scale[1]` (`FUN_00506770`, 5 runs), `hit.chance_scale[1]` (the same function, 79 runs: a
  chance roll each frame the art runs), `scale.559BF0[0]` and `[1]` (1 run each). No crash dump, no visible change in the game.
- **Not reached by anything tried** (melee swings, getting hit, inventory / character / belt tooltips, hotkeys): the six `level.factor` sites except the function
  itself (which the self test calls directly), the other three `hit.effect_scale` and three `hit.chance_scale` sites (the other three hit handlers belong to
  other combat art states: `FUN_00537160`'s dispatcher calls them by the creature's state `[creature+0x150]`), `scale.559BF0[2]`, the five
  `difficulty.factor` sites (`FUN_0056B130`, callers `0x4CD3CB`, `0x4CD489`, `0x532047`) and `difficulty.scale`. The inlined level sites are in
  `FUN_0050E6C0` (a hit handler) and `FUN_005893B0` (called from UI code `0x6C2AE3` and `0x6E4BC1`).
- The monsters do not attack a hero that stands still after `gear.world.spawn` (they are created like script NPCs); a click on them wakes them up.

## B14 Spell parameters inside the effect function `FUN_00571710` (12 hunks) - characterised

Immediate values pushed as arguments for individual spells change: `5 -> 0x14` (x2), `0xF -> 0x14` and `0xF -> 0x78`, `0x482 -> 0x496`
(a text/id), the float `0.15 (0x3E19999A) -> 0.2 (0x3E4CCCCD)` four times and one `0.15 -> 1.2 (0x3F99999A)`, and one call
(`push 0x44F; call 0x4D1930 ...` -> `push 0x35D; ... call 0x672F70`: a different text is shown). These are spell-specific numbers that are
not in the T2 table. Needs a hook around the spell effect (named per spell) or the constants as data.

**Resolved (read in the English exe, `FUN_00571710` is ENG; DE `0x5715D0`):** it is not a spell effect function but the **item bonus roller**:
the `cmp bx, 2/3/4` blocks (tiers) roll `rand(n)` and random float amplitudes into the item's bonus fields (`[ebp + 0xB6..0xC2, 0xEE]`) and
append text lines. The nine numeric hunks are arguments of those rolls (ENG `0x578BF0` 5 -> 20, `0x578C7A` 15 -> 20, `0x578C87` text 0x482 -> 0x496,
`0x578CC4` 15 -> 120, `0x578D07` 5 -> 20, `0x578D31/41/57/6D` 0.15 -> 0.2, `0x578D96` 0.15 -> 1.2). **Gear API:** `gear.on('bonus.constant', function(index,
vanilla, address) -> number)` (ten site hooks; a `push imm8` is displaced together with the `call rand` after it); `mods/reborn` returns ReBorn's numbers.
The other two hunks (`0x5789C4`, `0x578673`: a different tooltip text/format and the dropped `rand(15)` display) rewrite display code and are
not hooked: the text part is served by the text overlay (`text_checks.json`).

## B9 Effect-entry hook (`effect.add`) - decoded and re-created

`FUN_00562330` (DE; ENG `0x562470`) loops over a creature's effect entries (stride `0x16`: id word `+4`, maximum float `+0xA`, value `+0x12`) and adds a
value to the matching ones. ReBorn replaces the six bytes `fstp [ecx+0x12]; fld [ecx+0x12]` (ENG `0x56256D`) by a jump into a cave which, for the
local hero (`[list-0x39C]` == the hero's id) and an ability other than `0x35`, adds to the entry of the ability in use instead of the loop's
entry, skips the clamps and leaves the function; for ability `0x35` it stores nothing; and for every creature sets (flag `0x4000000`) or grows
(`0x20000000`) a counter at `[list-0x214]`. (Its hero path leaves one value on the x87 stack; the Lua version does not.) The AI calls the
function through a vanilla copy; here the stub ignores calls from the AI (return addresses `0x4DA04B..0x4DA23C`). **Gear API:**
`gear.on('effect.add', function(e) -> {value, effect, clamp, finish, stack})`; `mods/reborn` implements the cave.
