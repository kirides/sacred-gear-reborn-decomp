# ReBorn behaviours (first batch)

ReBorn is re-created as Lua on Sacred Gear's APIs, not copied as bytes. This file is the list of behaviours the
Lua has to reproduce: what vanilla does, what ReBorn does, and which Gear API the Lua version needs. Source of the
facts: `out/analysis.md` and `out/hunks.json` (generated by `tools/reborn_port.py`), the English decompile
(`decomp-sacred`) and the German -> English map. English addresses unless marked DE.

Status per row: **decoded** (what changes is understood), **characterised** (where and how it changes is known, the
game meaning is not), **engine** (not gameplay; Bild or the data layer covers it).

## B1 Table T1: skill-like effect table, 94 records of 0x78 bytes (ENG `0x94FE28`..`0x952A38`)

Looked up by `FUN_004d1af0(short id)` (the id is the first short; ids 1000, 1001, 1002, 1009, 1057 ...). About 80 callers
(`FUN_005bb010` creature action handler, `FUN_0056b130`, `FUN_005796a0` skill effects, `FUN_004fe870`, `FUN_005481f0`,
the UI `FUN_006d60e0`). The same ids are looked up in T2 when T1 does not have them (`FUN_004fe870`, `FUN_006d60e0`): T1 and T2
together are the ability table, T1 holding the ids from 1000, T2 the ids from 1.

Fields. **Proven** = a consumer reads it that way; **inferred** = shape of the values only.

| Offset | Type | Name (proposed) | Evidence |
|---|---|---|---|
| +0x00 | i16 | `id` | the lookup key |
| +0x04 | u32 | `name_text` | text id passed to the text function (`FUN_004d2020`: name + level) |
| +0x40 | f32 | `param_a` (5.0 -> 3.0/4.0/2.0) | inferred |
| +0x44 | f32 | `param_b` (3.0/6.0 -> 4.0) | inferred |
| +0x4C | u8 | `target_mode` | proven: passed on as the mode of `FUN_0051d840` / equals T2 +0x3C |
| +0x50 | f32 | `effect_base` | proven: `level * per_level + base` in `FUN_005bb010` case 0xBFC, `FUN_005796a0` case 0x3F7 (level clamped 1..100) |
| +0x54 | f32 | `effect_per_level` | proven (as above) |
| +0x58 | f32 | `effect2_base` | proven: second `fadd`/`fmul` pair in `FUN_005bb010` |
| +0x5C | f32 | `effect2_per_level` | proven |
| +0x60 | u32 | `time` (1000 -> 250) | inferred: the same value everywhere ReBorn edits it, a duration/cooldown in milliseconds |
| +0x64, +0x68, +0x6C | u32 | `param_c`, `param_d`, `param_e` | read by `FUN_005bb010`; not named |
| +0x74 | u32 | `flag` (1 -> 0) | inferred |

What ReBorn changes (all 94 records compared field by field, vanilla to ReBorn): `param_a` in 88 records (5.0 -> 3.0 / 4.0 / 2.0),
`param_b` in 71 (3.0 or 6.0 -> 4.0), `effect_base` in 70 (0.8 -> 1.45 or 2.4; 1.8 -> 3.8), `effect_per_level` in 44 (0.1 -> 0.05;
0.12 -> 0.10), `effect2_base` in 30 (55 -> 40, 1.8 -> 2.4, 39.5 -> 180), `effect2_per_level` in 28 (7 -> 5, 0.35 -> 0),
`time` in 16 (1000 -> 250), `target_mode` in 2 (1 -> 3), and a handful of other fields. These are balance numbers: the skills
scale differently with level. The per-record values are in `out-test/T1_slots.json` (generated by the tool; the ids come with them).

## B2 Table T2: combat-art / spell table, 70 records of 0x94 bytes (ENG `0x952ACC`..`0x955344`)

Looked up by `FUN_004d2310(short id)` (ids 1..). Consumers: `FUN_00571710` (the big effect function), `FUN_005b2600`,
the tooltip `FUN_006a6550`, `FUN_004fe870`, `FUN_006d60e0`.

| Offset | Type | Name (proposed) | Evidence |
|---|---|---|---|
| +0x00 | i16 | `id` | key |
| +0x3C | u8 | `target_mode` | proven: same use as T1 +0x4C |
| +0x42 / +0x44 | i16, i16 | `value[0]`: base, per level | proven: `FUN_006a6550`: `level * rec[+0x44] + rec[+0x42]` shown in the tooltip |
| +0x46 / +0x48 | i16, i16 | `value[1]` base, per level | proven (same) |
| +0x4A / +0x4C | i16, i16 | `value[2]` base, per level | proven |
| +0x4E / +0x50 | i16, i16 | `value[3]` base, per level | proven |
| +0x52 ..+0x7A | i16 | further per-level progressions (mana cost, cooldown, resist ...) | inferred: pairs and triples of small shorts |
| +0x76, +0x82 | u16 | edited 41 and 36 times by ReBorn (+0x82: 48 -> 65535, 120 -> 180) | not named |
| +0x84 | u32 | (700 -> 800, 50 -> 8, 60 -> 20) | inferred: a time |

ReBorn edits 59 of the 70 records, mostly the `value[]` pairs and the later progressions (halving or doubling per-level rates;
`value[1]` etc.), plus +0x3C..+0x64 in the first records. Field meanings of the later progressions need the effect code in
`FUN_00571710` read case by case (that function is about 3000 lines).

## Proposed Lua shape (to confirm before any Gear code)

```lua
local skills = gear.data.skills            -- T1, id-keyed
local s = skills[1000]                      -- nil if unknown
s.name_text; s.target_mode
s.effect_base = 1.45; s.effect_per_level = 0.05
s.time = 250
local arts = gear.data.combat_arts          -- T2
local a = arts[12]
a.value[1] = {base = 20, per_level = 3}      -- 1-based Lua array of 4 {base, per_level}
a.target_mode = 3
```

- The fields are named by the API (a layout table in Gear), not offsets, so the Lua reads like game data.
- Writes go through the game's own tables in the exe's `.data` (the engine reads them live), validated against the layout
  (type and range) and undone on unload; no byte patching in the mod.
- The ReBorn mod then holds a table of per-id edits (generated from the tool's diff: `{[1000] = {effect_base = 1.45, ...}}`),
  applied with `gear.data.skills:apply(edits)`. After a new ReBorn release the edit table is regenerated.

## B3 Data paths (engine)

`bin\%s` -> `SRB\%s`, `.\SRB\Balance.bin`, `MODELS` -> `SRmdls`, `CREATURE.PAK` -> `SRcreate.PAK`, `WEAPON` -> `SRwpon`, `ITEMS.PAK` -> `SRitm.pak`, `GLOBAL` -> `SRglbl` (the 14 `bin` -> `SRB` strings between `0x948D14` and `0x94C894` (DE) and about 20 more). In the mod these are not patched: the **Gear file overlay** serves `mods/reborn/data/...` for the original path, from the manifest. **Gear API:** `gear.files.overlay` (to add).

## B4 Text (engine)

`cTextTable::load` (ENG `0x80E680`) is rewritten to read `SRglbl.res` from disk and the embedded language resources are gone. In the mod: the text file is loaded through Bild's existing `cTextTable::load` hook (language import already does this), **Gear API:** `gear.text.load(path)` (to add; Bild has the hook, Gear does not expose it).

## B5 World object culling, `FUN_00566070` (DE `0x565F30`, 37 hunks)

- **Vanilla:** the object pass computes the visible rectangle from `(view - 1.0) / viewport-size` style expressions on the camera globals (`0xAD44E8..`, the 1.0 at `0x89066C`).
- **ReBorn:** the whole expression is replaced by constants from a small table in the appended code (`5.0`, `40.0`, `0.5` at `0x1AC7754..`): fixed margins, so objects are culled the same way at any screen size.
- **Status:** engine. SacredBild's resolution work already covers visibility at larger screens; nothing to port unless culling turns out different. (Checked by reading, not by running.)

## B6 Creature init, `FUN_004d4e50` (DE `0x4D4C90`, 14 hunks)

- **Vanilla:** the function sets `[creature+0x120]` to a per-type constant (`0x19`, `0x1D`, `0x28`, ...) and computes some values from flags (`neg/sbb/add 0x32`).
- **ReBorn:** the constants change (`0x19 -> 0x17`, `0x1D -> 0x21`, `0x28 -> 0x05`, ...), and one flag-dependent value becomes the constant `0x31`.
- **Status:** characterised; the meaning of `+0x120` (probably a behaviour class / ability set id of the creature type) is not decoded.
- **Gear API:** a creature **write** API for engine fields (`c:set_field(off, v)` or named fields) or a hook after creature creation (`gear.on('creature.created', c)`; to add).

## B7 Record layout shift, `FUN_005abd80` (DE `0x5ABCF0`, 31 hunks)

- **Vanilla:** the function keeps 16-bit values in the stack frame at `esp+0x3A`, `+0x3C`, `+0x3E`, ...
- **ReBorn:** the same values at `+0x3C`, `+0x40`, `+0x44`: the slots are widened to 4 bytes. This changes a data layout of the function's locals (it is a 3471-line function); ids or counts that exceed 16 bits are the likely reason (`balance.bin` gets entries 5171..5771 in its item id lists).
- **Status:** characterised, not decoded (needs the function read in full).
